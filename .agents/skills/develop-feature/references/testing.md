## 테스트

### 테스트 범위

- `domain`은 Spring Context 없이 단위 테스트한다.
- 단순 JPA Repository는 별도로 테스트하지 않는다.
- QueryDSL 등 직접 작성한 조회 로직은 persistence 테스트를 작성한다.
- `application`은 하위 레이어를 모킹한 단위 테스트를 기본으로 하지 않고, 실제 Spring Bean과 테스트용 데이터베이스를 연결한 통합 테스트를 작성한다.
- `api`는 service를 모킹한 Controller 단위 테스트를 기본으로 작성하지 않는다.
- 회원가입, 로그인, 토큰 인증 같은 주요 API 흐름은 `@SpringBootTest`와 MockMvc를 사용하는 API 통합 테스트로 검증한다.
- ArgumentResolver, Interceptor, 복잡한 요청·응답 직렬화처럼 API 계층 자체의 검증이 필요한 경우에만 Controller slice 테스트를 작성한다.
- 인증 테스트는 정상 발급뿐 아니라 잘못된 자격 증명, 비활성 계정, 만료시간, 토큰에서 복원되는 principal을 검증한다.
- 외부 시스템과의 실제 통신은 테스트에서 격리한다.

### 테스트 작성 원칙

- 모든 테스트 메서드에 검증할 조건과 기대 결과를 한글 한 문장으로 설명하는 `@DisplayName`을 명시한다.
- 매개변수화 테스트의 실행 이름은 `[{index}] {displayName}`으로 지정한다.
- 테스트는 구현 세부사항보다 외부에서 관찰 가능한 동작과 비즈니스 규칙을 검증한다.
- 하나의 테스트는 하나의 시나리오를 검증하며, 해당 시나리오의 결과를 확인하기 위한 여러 assertion은 허용한다.
- 테스트 코드는 재사용성보다 가독성과 명확성을 우선한다.
- 테스트만을 위한 불필요한 추상화, 상속 구조, 복잡한 헬퍼를 만들지 않는다.
- 테스트 데이터는 테스트의 의도를 이해하는 데 필요한 값만 명시한다.
- 테스트의 준비 조건, 실행 행위, 기대 결과가 코드에서 명확하게 드러나도록 작성한다.
- 중복 제거가 테스트의 의도를 숨긴다면 공통화하지 않는다.
- 반복 assertion은 시설 상태·가격 등 의미별로 묶을 수 있다. 검증 항목과 기대값을 유지하고, 중복률만 낮추기 위한 제외 설정이나 복잡한 공통 상속을 추가하지 않는다.
- 내부 메서드 호출 횟수나 구현 순서보다 최종 상태, 반환값 등 observable behavior를 우선 검증한다.
- 프로덕션 코드의 설계 원칙을 테스트 코드에 기계적으로 적용하지 않는다. 테스트 코드는 단순성과 명확성을 우선한다.
