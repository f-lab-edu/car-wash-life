## 책임과 추상화 판단

- 규칙에 필요한 데이터를 가진 객체가 판단하게 한다. 호출자가 객체의 상태를 꺼내 같은 규칙을 재구현하거나 그 객체에 다시 전달하는지 확인한다.
- 한 규칙·필드 목록을 여러 곳에서 함께 수정해야 한다면 소유자를 정한다. 입력 경계와 도메인 불변조건의 검증은 목적이 다르므로 단순 중복으로 제거하지 않는다.
- 한 객체의 계산은 우선 그 객체에 둔다. 여러 객체의 비교·선택이나 실제로 교체하는 전략은 별도 정책을 둘 근거가 된다. 클래스·Bean·주입을 늘릴 때 현재 요구로 비용을 설명한다.
- SOLID는 변경 이유와 의존 방향을 점검하는 기준으로 사용한다. 가상의 확장을 위한 인터페이스·계층은 추가하지 않고, 기존 경계도 실제 역할을 확인한 뒤 합친다.

## 도메인 구현

- 생성 의도가 다른 경우 이름 있는 생성 메서드로 구분하고, 유형과 기준 객체의 조합을 도메인 안에서 보장한다. 공개 빌더로 잘못된 조합을 만들 수 있게 하지 않는다.
- 함께 검증·전달하는 값은 값 객체로 묶을 수 있다. 요청 변환과 응답의 긴 필드 매핑은 API DTO 쪽에 두어 서비스가 처리 순서에 집중하게 한다. 단순 응답에 별도 Mapper 계층을 강제하지 않고, 도메인은 API 타입에 의존하지 않는다.
- 값 자체의 검증은 값 객체에, 상태의 의미에 따른 판단은 enum에 둔다. 이를 위해 별도 정책 계층을 자동으로 추가하지 않는다.
- 저장 없이 가능한 입력·생성 검증은 첫 저장·파일 쓰기 전에 마친다. 동시성에 필요한 조회·잠금과 실패에 대비한 트랜잭션·보상 처리는 유지한다.
- 값 객체는 입력·반환 배열과 컬렉션의 외부 변경도 막고 값 기반 동등성을 정의한다. record만으로 내부 값이 불변이 되지는 않는다([배열 예시](domain-examples.md)). JPA 임베딩은 기존 컬럼·갱신 제약과 재조회를 확인한다.
- 줄 수를 줄이기 위해 단순 대입을 숨기는 헬퍼를 늘리지 않는다.
- 저장된 enum 이름이나 API 항목 이름을 변경할 때 기존 데이터 읽기와 응답 계약의 영향을 확인한다. 코드 생성으로 이 호환성이 자동 보장된다고 가정하지 않는다.
- 예외 변환의 try는 해당 오류로 분류할 연산만 감싼다. 입력 오류 변환에 DB·파일 저장을 포함하지 않는다. 같은 범위에서 실패 종류를 구별해야 할 때 예외 타입을 검토하고, cause는 보존하되 응답에 노출하지 않는다.

## 패키지 및 타입 구성

- 한 기능의 요청과 응답이 한 쌍이면 `LoginDto.Request`, `LoginDto.Response`처럼 기능 단위 외부 클래스와 중첩 타입으로 묶는다.
- DTO 외부 클래스는 인스턴스화를 막는 private 생성자를 둔다. 상속을 막기 위한 `final`은 사용하지 않는다.
- ArgumentResolver는 인증 사용자처럼 여러 API에서 반복적으로 해석하는 값이나 복잡한 변환이 있을 때만 도입한다. 단순 RequestBody 바인딩을 위해 만들지 않는다.
- Entity 전용 패키지와 `*Entity` 접미사는 두지 않는다.
- 별도 도메인 모델은 비즈니스 규칙과 영속성 모델의 변경 이유가 실제로 달라질 때 분리한다. 계층 분리만을 목적으로 Entity와 동일한 도메인 모델 및 매핑 코드를 미리 만들지 않는다.
- API, service, persistence 간 타입 의존 방향을 변경할 때는 관련 호출부와 매핑 책임을 함께 검토한다.
