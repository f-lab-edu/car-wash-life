## 설계 원칙

- 객체와 모듈을 설계하거나 변경할 때 SOLID 원칙을 준수한다.
- 하나의 클래스나 메서드가 서로 다른 변경 이유를 갖지 않도록 책임을 분리한다.
- 기능 확장마다 기존 코드의 반복적인 수정이 필요한 구조라면 변경 지점을 분리할 수 있는 설계를 검토한다.
- 하위 타입은 상위 타입이 보장하는 계약을 깨뜨리지 않아야 한다.
- 사용하지 않는 기능에 의존하도록 큰 인터페이스를 설계하지 않는다.
- 의존성 역전이 필요한 경계에서는 상위 수준의 정책이 구체적인 구현 세부사항에 직접 의존하지 않도록 한다.
- SOLID 준수를 이유로 필요하지 않은 인터페이스, 계층 또는 추상화를 미리 추가하지 않는다.
- 설계 원칙 간 충돌이 있거나 적용 여부가 불분명한 경우, 원칙을 기계적으로 적용하지 않고 현재 요구사항과 변경 가능성을 기준으로 판단한다.

## 도메인 구현

- 생성 의도가 다른 경우 이름 있는 생성 메서드로 구분하고, 유형과 기준 객체의 조합을 도메인 안에서 보장한다. 공개 빌더로 잘못된 조합을 만들 수 있게 하지 않는다.
- 함께 검증·전달하는 값은 값 객체로 묶을 수 있다. API DTO는 도메인 값으로 변환하고, 도메인이 API 요청 타입에 의존하지 않게 한다.
- 값 자체의 검증은 값 객체에, 상태의 의미에 따른 판단은 enum에 둔다. 이를 위해 별도 정책 계층을 자동으로 추가하지 않는다.
- 저장이 필요 없는 생성 검증은 도메인 객체를 완성한 뒤 저장하도록 배치한다. DB 저장 실패에 대비한 트랜잭션은 유지한다.
- 값 객체는 외부에서 변경할 수 없게 하고 값 기반 동등성을 정의한다. JPA 임베딩 시 기존 컬럼·갱신 제약과 저장 후 재조회 동작을 확인한다.
- 메서드는 호출 흐름과 관련 책임을 따라 가까이 배치한다. 줄 수를 줄이기 위해 단순 대입을 숨기는 헬퍼를 늘리지 않는다.
- 저장된 enum 이름이나 API 항목 이름을 변경할 때 기존 데이터 읽기와 응답 계약의 영향을 확인한다. 코드 생성으로 이 호환성이 자동 보장된다고 가정하지 않는다.
- 예외를 다른 예외로 변환할 때 원인을 cause로 보존하고, 응답에는 공개 오류 코드와 메시지만 사용한다. catch 범위와 예외 분류의 변경은 별도 설계 판단으로 다룬다.

## 패키지 및 타입 구성

- 기능 코드는 `application/{feature}` 아래에 `api`, `domain`, `service`로 구분한다.
- Controller는 `api`에 두고, API 요청·응답 DTO는 `api/dto`에 둔다.
- 한 기능의 요청과 응답이 한 쌍이면 `LoginDto.Request`, `LoginDto.Response`처럼 기능 단위 외부 클래스와 중첩 타입으로 묶는다.
- DTO 외부 클래스는 인스턴스화를 막는 private 생성자를 둔다. 상속을 막기 위한 `final`은 사용하지 않는다.
- ArgumentResolver는 인증 사용자처럼 여러 API에서 반복적으로 해석하는 값이나 복잡한 변환이 있을 때만 도입한다. 단순 RequestBody 바인딩을 위해 만들지 않는다.
- 현재는 JPA Entity를 `application/{feature}/domain`에 두고 도메인 모델로 사용한다. Entity 전용 패키지와 `*Entity` 접미사를 두지 않는다.
- Spring Data Repository는 `infrastructure/persistence`에 둔다.
- 별도 도메인 모델은 비즈니스 규칙과 영속성 모델의 변경 이유가 실제로 달라질 때 분리한다. 계층 분리만을 목적으로 Entity와 동일한 도메인 모델 및 매핑 코드를 미리 만들지 않는다.
- API, service, persistence 간 타입 의존 방향을 변경할 때는 관련 호출부와 매핑 책임을 함께 검토한다.
