# 리뷰 반영

공통 기준은 프로젝트 `AGENTS.md`를 따른다. 해당 작업에 연결된 참고 지침만 읽고, 위임할 때 필요한 문서 경로를 전달한다.

## 지적 확인

PR 번호, base/head와 분석 커밋을 확인하고 실제 리뷰·후속 답변·관련 코드·테스트를 읽는다. 마지막 커밋 검토와 PR 전체 검토를 구분한다.
이미 반영된 지적과 남은 변경을 구분한다. 오래된 SonarCloud 결과를 현재 코드의 실패로 단정하지 않는다.
사용자가 한 항목씩 논의하기를 원하면 현재 항목에 집중한다. 설명·설계 요청은 구현 승인으로 해석하지 않는다.

## 판단과 반영

지적의 의도, 현재 문제, 변경 후 구조와 호환성 영향을 설명한다. 필요하면 AS-IS/TO-BE 코드로 차이를 보여준다.
다른 코드에 적용할 때는 지적을 `발생 조건 → 잘못 놓인 책임·경계 → 보존할 동작`으로 바꾸고, PR 전체 변경과 관련 호출부에서 같은 조건을 찾는다.
후보마다 수정·이미 충족·적용 제외를 근거와 함께 판단한다. 특정 Policy 삭제나 enum 도입을 모든 코드의 규칙으로 일반화하지 않는다.
지침 개선도 요청받았다면 재현된 누락·충돌만 담당 문서에 통합하고, 중복 지침을 대체한다. PR 이력·분석표는 상시 지침과 분리하고 긴 예시는 필요할 때 읽는 참고 문서에 둔다.
수정이 허용되면 선택한 범위만 직접 처리하거나 `implementer`에 위임한다. 설계 판단이 남으면 `architect`를 사용한다.

## 검증과 보고

규칙을 옮겼다면 원래 시나리오를 유지하며 새 책임에 맞춰 테스트를 배치한다.
JPA 변경은 저장·재조회와 관계를, 저장 항목 이름 변경은 과거 데이터 읽기를, 예외 변환은 cause와 공개 응답을 검증한다.
SonarCloud는 열린 이슈와 Quality Gate 실패를 구분하고 중복 블록을 실제 코드와 비교한다.
변경 후 `verifier`로 독립 검토하거나, 직접 검토한 경우 그 한계를 밝힌다.
결과에는 판단 근거, 반영한 지적, 검증과 한계를 포함한다. 여러 PR은 요청한 순서로 검증을 마친 뒤 다음 PR에 반영하고, 새로 확인한 지침의 결함도 같은 순서로 보완한다.
