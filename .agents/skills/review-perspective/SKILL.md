# 리뷰 판단 기준

리뷰 의견을 그대로 수용하거나 일괄 거절하지 않는다. 의도와 실제 호출 경로를 확인하고, 필요한 변경과 유지할 이유를 구분해 근거를 설명한다. 설명만 요청한 경우 판단을 먼저 제시한다.

- **필요성과 범위:** 현재 요구와 이슈의 사용자 흐름을 먼저 확인한다. 새 의존성·계층·데이터·도구·문서는 현재 문제에 대한 이득과 도입 및 유지 비용을 비교한다. 포트폴리오 작업에서는 실행·재현의 편의와 핵심 경험을 설명하는 데 기여하는지도 고려한다.
- **검증 책임:** 요청 검증과 도메인 검증의 실제 생성 경로와 목적을 각각 확인한다. 요청에서만 생성되는 조건의 동일한 검증은 관리 비용을 고려한다. 여러 경로에서 쓰는 값, 상태 불변조건, 파일·외부 데이터의 무결성은 중복이라는 이유만으로 제거하지 않는다. 검증 위치를 옮겨도 오류 응답과 특수 입력 처리를 유지한다.
- **복잡도와 공통화:** 주석은 의도나 의미가 코드에서 드러나지 않을 때 보완한다. 이름·순서·쿼리의 일부가 비슷하다는 이유만으로 추상화하지 않고, 함께 바뀌는 규칙인지와 변경 시 얻는 이득을 확인한다. 같은 원인이 있는 유사 코드도 살피되 맥락이 다르면 구분한다.
- **성능:** 성능 우려는 추측만으로 결론내리지 않는다. 시나리오, 데이터·실행 조건, 측정값을 분리해 제시하고 확인하지 않은 것은 명시한다. 성능 개선을 기술 도입의 근거로 삼는다면 측정으로 확인하고, 도입 비용과 실제 복잡도도 비교한다.
- **전달 방식:** 결론과 근거를 짧게 제시하고, 상세 설명은 판단에 필요한 만큼만 제공한다. 성능 기록은 시나리오·조건·결과가 한눈에 보이게 작성한다. 기록 위치와 커밋 여부는 사용자가 정한 방침을 따른다.

판단 후 변경이 허용된 범위만 적용하고, 관련 동작을 검증한다. 적용하지 않은 의견은 이유를 밝힌다.
